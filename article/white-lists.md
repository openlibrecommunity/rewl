# Белые списки

by Mikhailo Trubochki

Прошлой весной zarazaex разобрал белые списки на Хабре. Статья собрала 636 плюсов и 281 тысячу просмотров. Потом его аккаунт заблокировали за создание дополнительных аккаунтов. Сама статья осталась, но за четыре месяца часть её измерений устарела.

Я перепроверил всё заново. Где старые выводы подтвердились, я это отмечаю. Где сломались, показываю новые данные. Плюс разбираю то, чего в первой статье не было: устройство самого ТСПУ по утёкшей документации RDP.ru и обход через CDN.

Весь код и данные лежат в openlibrecommunity/rewl.

## Как читать эту статью

Каждый технический вывод я помечаю одним из трёх статусов.

Измерено. Я запускал команду через интерфейс с белыми списками, вот вывод, вот дата.

Из документации. Утверждение опирается на конкретную главу утёкших материалов RDP.ru.

Гипотеза. Механизм похож на правду, но измерения его пока не подтвердили.

Первая статья смешивала эти три вещи. Masscan находил отвечающие IP, а вывод звучал как "полный список белых адресов". Это разные утверждения, и дальше я показываю разницу.

## Что такое белые списки

Открывается vk.com, но не открывается google.com. Сигнал есть, байты идут, а ТСПУ решает какие пропустить. Классическая блокировка работает по чёрному списку: запрещено X, Y, Z, остальное можно. Белый список переворачивает правило. Запрещено всё, разрешено избранное.

Белые списки работают на L3 и L4. ТСПУ сверяет IP назначения, протокол и порт с разрешёнными правилами. Совпадение пропускает пакет. Для остальных соединений мы наблюдаем таймаут или подставной RST, в зависимости от оператора и правила.

```text
пакет -> [IP, протокол и порт разрешены?]
           да  -> PASS
           нет -> DROP или подставной RST
```

Проверка SNI, TLS fingerprint и протокольных сигнатур относится к обычной работе ТСПУ. Она действует поверх белых списков, но не является их признаком. Поэтому L3/L4 и DPI дальше рассматриваются отдельно.

## Где применяются правила

Утёкшие документы RDP.ru описывают два эшелона ТСПУ. Первый распознаёт приложения через DPI. Второй применяет крупные списки IP, подсетей, портов и протоколов через BGP, FlowSpec или API. Белые списки относятся ко второму классу правил.

ЦСУ формирует и распространяет списки. Оператор подключает и обслуживает площадку. Подробное устройство байпаса, балансировщика и EcoFilter лежит в `data/tspu/`, но для сканирования важен результат: правило применяется после терминации абонентской сессии и до выхода в интернет.

## Новый скан

5 августа 2026 года я запустил новый скан через мобильный интернет МегаФона в Иваново. Белые списки в этой точке работают почти круглосуточно. Тариф на результат не влияет. Номер вышки я не фиксировал.

Источник диапазонов: `scanitex.com/resources/ipdb/ipv4/ru.zone`. Файл содержал 11 180 CIDR и 44 900 160 адресов.

Первый проход:

```sh
rewl ipload ru
rewl ipcount ru
sudo rewl scan ru --iface enp0s20u7 --ports 80,443 --rate 3000
sudo rewl scan ru --resume
rewl analyze ru
```

Он шёл с 16:04 до 20:50 UTC, 4 часа 45 минут. Masscan нашёл 32 002 endpoint'а на 29 438 уникальных IP. Этого хватило, чтобы определить 2504 подсети `/24` с доступными адресами.

Второй проход проверил только эти подсети:

```sh
sudo rewl refine ru \
  --iface enp0s20u1 \
  --ports 80,443 \
  --rate 1000 \
  --retries 3
```

Вместо 44,9 миллиона адресов осталось 641 024. Masscan нашёл 150 703 endpoint'а на 91 648 IP. Затем nmap перепроверил каждый адрес батчами с checkpoint:

```sh

  --iface enp0s20u1 \
  --ports 80,443 \
  --rate 500 \
  --retries 3 \
```

Nmap подтвердил 111 918 endpoint'ов на 72 076 уникальных IP.

## L3 и место фильтра

Старый эксперимент с TTL воспроизводится по той же схеме. Ответ от разрешённого сервера приходит с TTL около 50. Это соответствует удалённому узлу. RST для заблокированного назначения приходит с TTL около 62. Такой пакет создал узел рядом с абонентом.

```text
абонент -> сеть доступа -> ТСПУ -> сеть оператора -> интернет
```

TTL указывает расстояние до источника ответа, а не модель оборудования. Он не показывает точную стойку, порт или порядок всех компонентов. Утёкшая документация уточняет место: ТСПУ ставят после терминации абонентской сессии и до пограничного выхода. На площадке могут стоять BRAS, CG-NAT, байпас, балансировщик и несколько фильтров.

## Обычный ТСПУ поверх белых списков

Белые списки пропускают соединение до разрешённого IP и порта. После этого обычный DPI продолжает проверять SNI и другие признаки протокола. Архив twl проверял три разрешённых IP: Яндекс, VK и Mail.ru. Через каждый отправляли TLS ClientHello с четырьмя SNI.

| SNI | Результат |
|---|---|
| telegram.org | проходит |
| youtube.com | проходит |
| google.com | проходит |
| twitter.com | режется |

Единого правила «заблокированный домен не проходит как SNI» нет. Twitter режется, Telegram и Google проходят. Фильтр применяет узкий список и может отличаться между площадками.

Для проверки нужен `curl --resolve`, а не обычный запрос:

```sh
curl --interface enp0s20u7 \
  --resolve twitter.com:443:77.88.55.242 \
  https://twitter.com/ -vk
```

IP назначения остаётся адресом Яндекса. SNI и HTTP Host становятся `twitter.com`. Так L3 остаётся постоянным, меняется только L7.

## 49 тысяч доменов на найденных IP

IP мало полезен без имени. TLS требует SNI, CDN маршрутизирует по Host, а некоторые серверы отдают заглушку при запросе по адресу. `rewl sni` собрал домены через обычный домашний интернет:

```sh
rewl sni ru --workers 200 --timeout 3s
```

Команда использовала шесть источников:

1. PTR reverse DNS.
2. SAN и CN сертификата без SNI.
3. Повторный TLS handshake с PTR и найденными именами как SNI.
4. HTTP redirect.
5. HTTPS redirect без SNI.
6. HTTPS redirect с найденным SNI.

За 10 минут 33 секунды обработано 72 076 IP и найдено 49 217 уникальных доменов. У каждого имени в `data/pub/ru.sni.yaml` записаны связанные IP и способы обнаружения.

| Источник | Домены |
|---|---:|
| PTR | 16 832 |
| TLS без SNI | 29 920 |
| TLS с найденным SNI | 31 664 |
| HTTP redirect | 2 478 |
| HTTPS без SNI | 1 391 |
| HTTPS с SNI | 5 031 |

Сумма больше 49 217, потому что одно имя подтверждается несколькими способами. Файл не утверждает, что каждый SNI проходит DPI. Он показывает домены, связанные с доступными IP. Проходимость проверяется отдельно через `curl --resolve`.

## UDP разрешили

В первой статье UDP 443, 53 и 51820 не отвечали. В августе UDP начал проходить в Иваново.

Это не означает, что заработал обычный WireGuard. ТСПУ распознаёт его handshake по сигнатуре и режет уже как протокол. QUIC и DNS работают, когда их адрес и порт разрешены. UDP теперь проходит L3/L4, а DPI продолжает блокировать распознанные протоколы.

## DNS

Старая картина МегаФона: внешние резолверы не отвечали, работал DNS оператора. Сейчас DNS стал одним из основных каналов обхода. WhiteDNS, Slipnet, MasterDnsVPN и Zanoza строят туннель через доступные резолверы.

Следующий скан проверит UDP и TCP 53 по российским диапазонам через МегаФон. Открытый порт ещё не делает сервер DNS-резолвером, поэтому каждый адрес получит валидный запрос, проверку ответа и замер скорости. После этого `rewl` опубликует актуальный список резолверов МегаФона.

Практический процесс такой:

1. Masscan находит адреса с доступным портом 53.
2. Проверяющий модуль отправляет DNS-запрос к контрольному домену.
3. Адрес проходит только при корректном ответе.
4. Второй тест измеряет способность резолвера передавать данные туннеля.
5. Клиент выбирает адрес по потерям и задержке.

DNS-туннель работает медленнее TCP и CDN. Провайдер вынужден оставить рабочий DNS для разрешённых доменов, поэтому канал сохраняется даже при узком белом списке.

## Четыре месяца спустя

### Reality уходит, XHTTP заменяет его

Reality почти перестал работать у части провайдеров. Где-то он ещё проходит, но строить новый конфиг вокруг него уже нет смысла.

Вместо него используют XHTTP. Он разделяет upload и download на HTTP-запросы, поддерживает packet-up, multiplexing и padding. Прямой XHTTP по-прежнему требует IP из белого списка. Транспорт решает проблему DPI, а доступный IP решает L3.

Если XHTTP недоступен в клиенте, лучше выбрать другой поддерживаемый протокол, чем ставить старый Reality как единственный вход.

### Yandex Cloud Functions

Endpoint `functions.yandexcloud.net` остаётся доступным у многих операторов. Функция может принять WebSocket или HTTP и передать трафик на внешний сервер. Готового поддерживаемого клиента OLC нет. Проект `noiseonwires/yac-ws-bridge` показывает рабочую схему с локальным адаптером.

Ограничения: холодный старт, лимиты выполнения, карта для активации облака, скорость ниже прямого VPS. Метод жив, продуктовой реализации нет.

### Yandex API Gateway

Метод закрыт простым изменением L3. IP API Gateway убрали из белых списков. OpenAPI-конфиг, сертификат и собственный домен не помогают, когда пакет не доходит до шлюза.

Это хороший пример двух уровней фильтра. Внутри шлюза проксирование продолжает работать. Абонент потерял маршрут до входного адреса.

### VK TURN relay

`cacggghp/vk-turn-proxy` использует TURN VK как relay. Сам протокол TURN продолжает работать. VK ограничил скорость примерно до 250 Кбит/с, поэтому реализация подходит для SSH и аварийного доступа, но уступает olcRTC как общий туннель.

### DNS-туннели

StormDNS, MasterDnsVPN и Slipstream используют доступные резолверы как транспорт. Клиент кодирует данные в DNS-запросах, резолвер передаёт их авторитетному серверу домена, сервер возвращает ответ тем же путём. Метод работает через UDP или TCP 53. Скорость зависит от резолвера, кэша, размера ответа и шейпинга. Клиенту нужны параллельные запросы, автоматический перебор, повторы и смена резолвера.

### olcRTC

olcRTC вырос из пре-альфы в beta. Он переносит TCP через WebRTC/SFU. Оператор видит соединение с разрешённым сервисом видеозвонков.

```text
приложение
  -> SOCKS5 127.0.0.1:8808
  -> olcRTC client
  -> Jitsi, Telemost или WB Stream
  -> olcRTC server
  -> интернет
```

Туннель шифрует payload через XChaCha20-Poly1305 и мультиплексирует потоки через smux. Доступны четыре транспорта:

| Транспорт | Назначение |
|---|---|
| datachannel | быстрый путь для Jitsi |
| vp8channel | основной видеопуть для WB Stream и Telemost |
| seichannel | payload в H264 SEI с ACK и повторами |
| videochannel | экспериментальные QR и tile-кадры |

Серверы SFU сами находятся в белом списке. olcRTC не требует IP вашего VPS в БС: серверная сторона подключается к той же комнате из обычного интернета. Готовые клиенты: owenclave, veil и olcbox.

## CDN + XHTTP

Крупные российские CDN нельзя убрать из белого списка без массовой поломки сайтов. Клиент подключается к edge-узлу CDN, а CDN передаёт HTTP-запрос на ваш origin.

```text
телефон на LTE
  -> Timeweb или Beeline CDN, IP в БС
  -> origin VPS в России, nginx
  -> Xray XHTTP inbound
  -> exit-нода за рубежом
  -> интернет
```

Оператор видит HTTPS к CDN-домену. CDN видит обычные HTTP-запросы к origin. XHTTP кодирует upload как последовательность запросов.

Timeweb storage CDN принимает GET, HEAD и OPTIONS, но блокирует POST и WebSocket Upgrade. Поэтому gRPC и WebSocket не проходят. XHTTP работает в режиме `packet-up` с `uplinkHTTPMethod: "GET"`.

Минимальная серверная часть:

```nginx
server {
    listen 80;

    location /api/uploadFile/ {
        proxy_pass http://127.0.0.1:10003;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_request_buffering off;
        proxy_buffering off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        client_max_body_size 0;
    }
}
```

Xray inbound:

```json
{
  "listen": "127.0.0.1",
  "port": 10003,
  "protocol": "vless",
  "streamSettings": {
    "network": "xhttp",
    "xhttpSettings": {
      "mode": "packet-up",
      "path": "/api/uploadFile/",
      "scStreamUpServerSecs": "20-80",
      "sessionKey": "X-Upload-Token",
      "sessionPlacement": "header",
      "seqKey": "chunk_id",
      "seqPlacement": "query"
    }
  }
}
```

Клиент должен использовать тот же path, sessionKey и seqKey. Для Timeweb нужен GET:

```json
{
  "path": "/api/uploadFile/",
  "uplinkHTTPMethod": "GET",
  "sessionKey": "X-Upload-Token",
  "sessionPlacement": "header",
  "seqKey": "chunk_id",
  "seqPlacement": "query",
  "xmux": {
    "hMaxReusableSecs": "1800-3000",
    "cMaxReuseTimes": 1000,
    "maxConcurrency": "16-32",
    "hKeepAlivePeriod": 20000,
    "hMaxRequestTimes": "600-900"
  }
}
```

CDN закрывает idle-соединения. `scStreamUpServerSecs` и `hKeepAlivePeriod` поддерживают активность. Кэш надо отключить, иначе edge начнёт возвращать старые ответы. Beeline CDN допускает другой HTTP-метод и требует отдельной проверки.

CDN остаётся второстепенным вариантом. Он всё равно зависит от IP edge-узла в белом списке. Провайдер может убрать диапазон CDN, запретить HTTP-метод, включить кэш или уменьшить таймаут. Конфигурации нужны несколько CDN-профилей.

| прямой VLESS + XHTTP | да | высокая | средняя | основной прямой метод |
| CDN + XHTTP | edge CDN должен быть в БС | высокая | средняя | второстепенный метод |
| Yandex Functions | нет | средняя | средняя | работает, нет готового продукта |
| olcRTC | нет | средняя | зависит от SFU | beta |
| DNS-туннель | нет | низкая | зависит от резолвера | работает |
| VK TURN relay | нет | низкая | низкая | шейпинг около 250 Кбит/с |
| API Gateway | нет | отсутствует | закрыт | IP убрали из БС |

Для рабочего доступа с ноутбука я бы начал с CDN + XHTTP и держал olcRTC как независимый резерв. DNS-туннель нужен для восстановления связи и обновления конфигов. Прямой VPS имеет смысл, если его подсеть стабильно проходит у вашего оператора.

Один профиль не переживёт смену правил. Клиенту нужны несколько входов, автоматическая проверка и failover. Российские сервисы лучше отправлять напрямую через split tunnel. Это снижает задержку и не смешивает банковские приложения с зарубежным выходом.

MAX отдельно собирает признаки VPN на устройстве и отправляет их на сервер. Этот канал не относится к ТСПУ, но влияет на эксплуатацию обхода. Разбор механизма опубликован на Хабре: https://habr.com/ru/articles/1026500/. Не запускайте MAX в одном сетевом профиле с туннелем, если можете разделить приложения или устройства.

## Итог

Широкий masscan нашёл 29 438 IP. Повтор по найденным `/24` поднял число до 91 648. Nmap подтвердил 72 076 адресов и 111 918 endpoint'ов. Один широкий проход пропускал больше половины доступных серверов.

Yandex.Cloud дал 14 509 IP. Вместе ASN Яндекса заняли четверть списка. По PTR, TLS-сертификатам и redirect найдено 49 217 доменов. Все результаты опубликованы в `data/pub/`.

Следующий отдельный прогон по порту 53 даст проверенный список DNS-резолверов МегаФона.

XHTTP заменяет Reality для прямых и CDN-соединений. CDN остаётся дополнительным входом через разрешённый edge. olcRTC использует SFU, DNS-туннели используют резолверы оператора. Клиенту нужен failover между разными транспортами.
